# Ingestion and provider limits

File/email source config accepts positive integer `max_file_bytes` / `max_message_bytes` (default 25 MiB), `max_batch_bytes` (64 MiB), and `max_batch_items` (1,000). CLI source add accepts the corresponding `--max-file-bytes`, `--max-message-bytes`, `--max-batch-bytes`, and `--max-batch-items` flags; existing source config can be updated through the dashboard API or storage API. Values must not exceed 2,147,483,647. Increase explicitly for larger supported workloads after sizing the deployment.

File reads are bounded while streaming, including growth after stat. Oversize files produce an error event and stay eligible for a later retry; no truncated item is created. Batch boundaries preserve unread files. Email requests bounded IMAP literals (limit plus one sentinel byte); oversize mail fails sync without advancing the persisted cursor. Batch boundaries leave remaining messages for the next sync. An individual message must fit both its per-message limit and batch limit. Raw limits bound payload bytes, not total JavaScript RSS: decoded MIME, normalized objects, indexes, directory listings, and parser overhead add memory.

AI settings accept `ai_timeout_ms` (30,000), `ai_max_input_bytes` (1 MiB serialized item), and `ai_max_response_bytes` (1 MiB). The timeout aborts fetch and body consumption. Input/response limits reject rather than truncate. Configure these keys in `config/settings.json` while the store is stopped, or through the storage API inside a store transaction. Timeout and limit errors preserve sync retry eligibility. HTTP failure/invalid model JSON retains the existing safe fallback policy. No message is sent to the provider when the input cap is exceeded.

Browser regression: `npx playwright install chromium` then `npm run test:browser`. CI installs Chromium separately; runtime dependencies are unchanged. The test runs the real dashboard JavaScript and verifies token rotation, old-token rejection, saving, reload, URL scrubbing, and page errors.
