## Scope and baseline

Intake remains a local-first CLI/dashboard with persisted items and configurations and email, webhook, Slack, GitHub/Jira/Linear/ClickUp adapters. The [previous audit](repository-hardening-2026-10-13-config.md) supplies context for unchanged resource and config contracts.

Logs and hashes are recorded in [verification.json](artifacts/2026-10-13-metadata-sweep/verification.json); verbose logs are ignored.

## Findings and changes

| Problem and root cause | Fix and files | Proof and compatibility |
| --- | --- | --- |
| Migration coerced arbitrary persisted schema values with `Number(value || 0)`. Invalid strings produced NaN, bypassed the future-version guard, and were rewritten as the current schema. Scalar/array metadata could also be overwritten. | `src/migrations.js` checks an object record and nonnegative safe-integer schema before updating metadata. | `tests/migration-integrity.test.js` confirms rejection without changing metadata bytes for malformed records, null/boolean/array/blank/negative/fractional versions, and future schemas. Missing files still initialize; pre-versioned objects, zero and numeric-string versions retain compatibility. |
| Restore staging called initialization, so malformed archived metadata could be silently repaired and replace a healthy destination. | The same migration guard stops staging before destination replacement; existing restore rollback/cleanup handles the error. No second validator or alternate restore path was added. | A checksum-correct archive with invalid embedded schema previously restored successfully. The regression now confirms forced restore fails and preserves the destination metadata. |
| Doctor's direct API dereferenced null metadata and treated missing metadata as a valid default record. Diagnostic schema conversion was inconsistent with migration. | `migrationStatus` reads persisted metadata without fallback substitution, returns structured failure for missing/corrupt content, and propagates filesystem errors other than absence. `src/doctor.js` uses that shared diagnostic. | Tests cover null, malformed JSON, invalid schema and absent metadata without rewriting it. The direct doctor API returns a failed schema check. CLI doctor still initializes first and fails during initialization on corrupt metadata; this does not promise a JSON diagnostic for every CLI initialization failure. |
| Parsed falsy lock-owner records were treated as absent owners and removed without explicit force. | `src/store-lock.js` distinguishes undefined (no parsed record) from persisted null/false/zero/empty-string ownership evidence. | `tests/lock-evidence.test.js` proves ordinary recovery neither invokes repair nor removes evidence. Explicit force can recover these unreadable records after operators stop writers. Even force refuses a live process or another host and preserves those locks. |

Implementation commits: `b8a6089` (metadata/doctor) and `278ee69` (ownership evidence). README documents inspection and recovery requirements. No dependencies, environment variables, network protocols, normal CLI syntax, config/backup formats or supported item schemas changed. Malformed state now fails safely rather than being silently relabeled or removed. Numeric-string and pre-versioned object metadata remain accepted. No cross-repository change is required.

## Verification and limits

All 180 tests passed with normal concurrency in the isolated `npm run release:check`, including existing receiver crash/concurrency, import-journal, restore, action-policy, bounded-heap and resource regressions. That gate also passed lint, docs, smoke, eval, benchmark thresholds, retention heap proof, dependency audit, shipcheck, doctor and tracked-only packaging. Node 20.19 also passed all 180 tests with normal concurrency; Chromium and final documentation/package checks passed. Commands and log hashes are recorded in verification.json; exact-head CI is checked after push.

The new tests exercise actual restore staging and canonical sibling locks rather than merely duplicating validator logic. Four failures were demonstrated before their respective fixes. No test was skipped, timeout raised, assertion weakened or arbitrary delay added. This pass makes no performance, memory, token, output-size or dependency-reduction claim; the existing resource ratchets remain active. JavaScript syntax checks serve as the package's static gate; there is no separate compiler/typecheck target. No plugin-managed security scan or live provider exercise is claimed.

The trust boundary here is corrupted local persistence and interrupted-operation ownership. These changes do not add fsync/power-loss durability, hostile-filesystem protection, exactly-once provider delivery, or automatic reconciliation of uncertain outbound actions. Recovery still must not replay outbound actions. The explicit-force requirement presumes the operator has stopped writers when ownership cannot be read.

P0/P1/P2: no newly confirmed unresolved issue remains. Needs more evidence: live-provider and machine-power-loss guarantees remain outside this local proof. P3/not worth changing: speculative API rewrites, package removals and token/output churn were not admitted. No new human-review SignalBox item or cross-repository requirement was identified.
